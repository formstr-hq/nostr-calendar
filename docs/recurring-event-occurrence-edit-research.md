# Recurring Event Occurrence Edit Research

Status: research only. Nothing in this document is a protocol decision, accepted wire format, or implementation commitment.

## Question

Can recurrence-related Nostr tags represent cancellation or modification of one occurrence, and modification of one occurrence and all future occurrences, when an event may contain multiple RRULEs?

## Verified Current Behavior

### Recurrence tag shape

The application currently writes recurrence as an adjacent pair:

```json
[
  ["L", "rrule"],
  ["l", "FREQ=WEEKLY"]
]
```

The RRULE tag is exactly `["l", "<RRULE>"]`. There is no third element in the implemented tag.

- `src/nostr/events.ts` writes `["L", "rrule"]` followed by `["l", event.repeat.rrule]` for private events.
- `src/utils/parser.ts` handles an `["L", "rrule"]` tag by reading the second value from the immediately following tag.
- `src/utils/types.ts` stores one nullable RRULE string in `event.repeat.rrule`.
- `src/utils/repeatingEventsHelper.ts` expands one `RRule`, not an `RRuleSet`.
- `nips/NIP-52R.md` currently leaves individual occurrence changes undefined.
- The native recurrence engines do not currently support EXDATE or RDATE.

The current public-event writer in `src/nostr/events.ts` does not emit recurrence tags. This is existing behavior and is outside the decision being researched here.

NIP-32's current upstream text uses a third namespace marker when an `L` tag is present. The application's two-element `l` tag is therefore a project-specific compact form rather than the full upstream NIP-32 label form. This observation does not decide whether the format should change.

### Multiple RRULEs

Nostr permits repeated tags, so more than one `["l", "<RRULE>"]` can physically be stored in an event. The current application does not preserve or expand multiple rules. Depending on arrangement, the parser would read one rule or overwrite an earlier parsed rule.

If multiple rules were interpreted as a recurrence set, their natural behavior would be additive:

```text
all generated occurrences = union of the RRULE results
```

A Monday rule and a Wednesday rule would produce Mondays and Wednesdays. A later rule would not override an earlier rule, and another RRULE would not subtract a cancelled occurrence.

## Single-Occurrence Cancellation

iCalendar recurrence sets model cancellation with EXDATE. A possible Nostr representation, included only for discussion, is:

```json
["exdate", "<original-occurrence-start>"]
```

The value identifies the occurrence's original generated start. For an occurrence moved from 10:00 to 14:00, 10:00 is the value that would be excluded because that is the occurrence generated by the RRULE.

Potential expansion semantics would be:

```text
DTSTART + RRULE results + RDATE values - EXDATE values
```

Undecided details include the tag name, timestamp unit, date-time format, time-zone handling, duplicate values, and whether exclusions live on the parent or in separate Nostr events.

## Single-Occurrence Time Change

### EXDATE plus RDATE

For a time-only change that retains the parent duration and all other properties, one possible representation is:

```json
[
  ["exdate", "<original-occurrence-start>"],
  ["rdate", "<replacement-start>"]
]
```

This excludes the original start and adds another start. Its limitations are:

- RDATE does not identify which EXDATE it replaces.
- The added occurrence inherits the parent's duration.
- The added occurrence inherits the parent's title, description, location, participants, and other properties.
- Independent EXDATE and RDATE tags become ambiguous when several occurrences are changed.

### Recurrence-identified override

An override could explicitly identify the original occurrence and carry replacement fields. Conceptually it needs:

- Parent series coordinate.
- Original occurrence start, equivalent to `RECURRENCE-ID`.
- Replacement start and end.
- Changed event properties.

Possible storage locations remain undecided:

- Repeated structured tags on the parent event.
- A separate addressable Nostr event referencing the parent series.
- A non-addressable event whose identity is resolved through author, parent coordinate, and original occurrence start.

Parent tags keep the state together but require a custom encoding for arbitrary replacement fields. Separate events provide independent identity and replacement history but introduce fetching, authorization, deletion, and conflict-resolution questions.

## This and Future Occurrences

### Multiple bounded RRULEs on one parent

One option is to end the old rule before the selected occurrence and add another bounded or offset rule. Questions and limitations include:

- Every rule shares the event's one `start` value unless another start/effective-from convention is introduced.
- Every generated occurrence shares the same duration and event properties.
- A time change may require RRULE fields outside the currently supported subset.
- Overlapping rules can generate duplicate occurrences.
- COUNT must be recalculated when a count-limited series is divided.
- RRULEs are additive and do not provide ordered override semantics by themselves.

### Split into a linked series

Another option is to bound the original series before the selected occurrence and create a new series beginning at that occurrence. The new series could reference the old series through an undecided relation tag.

This permits a different start, duration, RRULE, and event properties. It also raises questions about calendar membership, invitations, RSVPs, busy-list entries, reminders, deletion, and whether clients present the two Nostr events as one logical series.

### This-and-future override

iCalendar defines `RECURRENCE-ID;RANGE=THISANDFUTURE`. A Nostr representation could model similar semantics without creating another series. Library and calendar-client support for this behavior is inconsistent, and the application would still need to define how fields, duration, and later exceptions are inherited.

## Nostr-Specific Tradeoffs

### Storing exceptions on the parent

- Editing one occurrence republishes the complete addressable parent event.
- Concurrent updates based on different parent revisions can lose each other's exception tags.
- Long-lived series can accumulate an unbounded number of tags.
- Clients cannot assume relays retain superseded addressable-event revisions.
- Private parent updates must reach all intended participants.

### Storing exceptions separately

- Clients need an additional query or index to discover all exceptions for a series.
- Authorization rules must establish who may modify or cancel an occurrence.
- Deterministic conflict resolution is needed when multiple events target the same original occurrence.
- Private overrides need their own encryption and distribution behavior.
- Deleting the parent series must define what happens to detached overrides.

### Interoperability and platform consistency

- Clients unaware of the extension may display cancelled occurrences or both original and replacement occurrences.
- JS, Android, and iOS recurrence engines must produce the same set for views, reminders, and widgets.
- Export to and import from ICS need mappings for EXDATE, RDATE, RECURRENCE-ID, and series splits.
- Device-calendar APIs have their own single-instance and future-instance behavior that may not map exactly to the chosen Nostr representation.

## Open Decisions

- Whether multiple RRULEs are in scope and, if so, how their tags are grouped.
- Whether cancellation uses a parent EXDATE tag or a separate cancellation event.
- Whether a time-only replacement uses RDATE or always uses an explicit override.
- How an override is identified and whether it is addressable.
- Which timestamp and time-zone representation identifies an original occurrence.
- Whether "this and future" uses a linked series split or range override.
- How COUNT and UNTIL are transformed during a split.
- How series-level and occurrence-level RSVPs interact.
- How private exceptions and new series are encrypted and distributed.
- How concurrent edits and conflicting overrides are resolved.
- What old clients display during any compatibility window.
- Which parts can be implemented consistently by all three recurrence engines.

No option above is selected by this document.
