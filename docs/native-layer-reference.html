Platform reference — read from android/ and ios/ source, not from docs/

What runs when the web view isn't

nostr-calendar's UI is one shared React codebase (src/). But underneath the Capacitor shell, Android and iOS each carry real native logic — background workers, alarm scheduling, a home-screen widget, calendar-file handling — that keeps working while the app is closed. This traces every class in android/app/src/main/java/app/formstr/calendar/ and ios/App/App/, plus the src/ code that feeds them, exactly as implemented today.

Companion to nostr-layer-reference.html, which covers the wire protocol this native code polls for. Existing docs/README were not consulted for either.

nostr-calendar · compiled 2026-07-26

What this is

A Capacitor app is usually a thin shell: native code that boots a WebView and gets out of the way. This one doesn't — Android alone has twelve native classes (2,700+ lines) doing scheduling, relay polling, and file handling that runs independently of the JS layer. The notification system in particular spans all three: JS decides whether to notify and writes the cache, native code decides when and actually fires the alarm.

The shared substrate

Native code and the web app never call each other directly for calendar data. They meet through one thing: Capacitor's Preferences plugin, which is localStorage to the JS layer and a plain key/value file to native code — SharedPreferences file CapacitorStorage on Android, UserDefaults keys prefixed CapacitorStorage. on iOS. No ContentProvider, no shared database, no other IPC exists between the two worlds.

JS writes

The web app is the only writer. It maintains the local event cache and, separately, a small set of keys that exist purely so native background code has something to read without a JS runtime.

cal:events cal:calendar_lists cal:notification-preferences cal:invitations bg:userPubkey bg:relays bg:lastLoginTime
↓ read-only
Native reads

NotificationWorker / IOSNotificationScheduler read cal:events, cal:calendar_lists, cal:notification-preferences to decide what to schedule. CalendarWidget reads cal:events only. InvitationWorker and BookingWorker Android-only read bg:userPubkey / bg:relays to know who and where to poll, and cal:invitations to avoid re-notifying about invites the JS layer already surfaced.

↓ produces
Native writes back

Only one thing flows the other way: each worker persists its own scheduling registry (cal:scheduled-event-notifications-v2 on Android) or last-fetch timestamps (bg:lastInvitationFetchTime, bg:lastBookingRequestFetchTime, bg:lastBookingResponseFetchTime) so the next run knows where it left off. The JS layer never reads these back.

Why this matters

None of the four Android workers ever run JS or touch the signer. InvitationWorker and BookingWorker query relays over a raw WebSocket and only ever look at gift-wrap envelope tags (#p, #k) and event ids — they never open a seal or rumor. Decryption requires the live signer, which only exists inside the running WebView.

JS notification layer src/

Everything above reads a cache. This is where the cache — and the decision to notify at all — gets written: src/stores/events.ts, src/stores/calendarLists.ts, src/utils/notificationPreferences.ts, src/utils/notifications.ts, and src/plugins/notificationScheduler.ts.

Three levers, one resolver notificationPreferences.ts

Whether a given event ever notifies, and how far ahead, is decided by one pure function — resolveNotificationPreference(eventPreference, listPreference), used via shouldScheduleNotifications() — folding together three independently-stored settings:

LeverStored whereSet by
Per-event enable/disableevent.notificationPreference — a nostr-published ["notification", value] tagno UI writes this — wins if present, but nothing in the app's editors ever sets it
Per-calendar enable/disableICalendarList.notificationPreference — a tag on the calendar-list event (32123), default "enabled"the calendar's manage dialog (CalendarManageDialog.tsx) — the actual on/off switch users operate
Reminder offsetscal:notification-preferences[eventId].offsetsMinutes — local-only, never published to nostrNotificationPreferenceEditor.tsx, in the event editor and the event-view quick-edit dialog
The resolution

eventPreference ?? listPreference ?? "enabled" — matches the native Java/Swift logic exactly. In practice, because no editor control sets the per-event flag, the calendar-level toggle is the only real "off switch"; the only per-event lever a user can actually operate is the offsets list itself — clearing it to empty means no reminders for that one event.

A fourth number, cal:settings.defaultReminderMinutes (global, nostr-synced, default 10), plays no part in this resolution — it only pre-fills a brand-new event's offsets field in the editor and is never consulted again after save.

Toggling a calendar's preference doesn't just apply forward: refreshNotificationPreferencesForCalendar(calendarId) (src/stores/events.ts) immediately re-syncs every event already in that calendar, five at a time via Promise.allSettled.

Save-flow order useEventSave.ts

Saving an event runs relay publishing and notification bookkeeping as two separate phases, in a fixed order: publish the event (32678/31923) → gift-wrap invites to any new participants → add/move it into the selected calendar (32123) → only then, outside the publish steps entirely, write or clear the local offsets preference → cancel whatever was previously scheduled for this event → resolve the three levers above → schedule fresh if the result is "enabled".

Every one of those cache writes independently calls reconcileNotificationSchedule() (src/plugins/notificationScheduler.ts) — a single save can trigger it four separate times (event write, preference write, cancel, schedule). That's safe by construction: the plugin forwards to Android's native reconcile(), which enqueues a unique one-time WorkManager job with ExistingWorkPolicy.REPLACE — four calls collapse into one real NotificationWorker.doWork() run.

Platform fork notifications.ts

Every exported function in src/utils/notifications.ts — scheduleEventNotifications, requestNotificationPermission, cancelEventNotifications, cancelAllNotifications, addNotificationClickListener — opens with if (!isNative) return …. Native scheduling is then delegated through the platform's NotificationScheduler plugin:

PlatformWhat actually schedules
AndroidscheduleEventNotifications computes a candidate list purely to show the user a "next reminder" preview, then just calls reconcile() — the real AlarmManager call happens entirely inside NotificationWorker.doWork(), re-reading the cache and re-expanding recurrence a second time with its own engine.
iOSscheduleEventNotifications calls LocalNotifications.schedule() directly, right here in JS, using the same candidate list and the same v2:eventId:occurrenceStart:mOffset key format IOSNotificationScheduler.swift uses independently on every launch/foreground/background/BGAppRefreshTask. Identical deterministic keys mean the two paths never conflict — they just redundantly agree.
WebNothing schedules. Worse: cal:events/cal:calendar_lists aren't even persisted across a reload on web — getSecureItem/setSecureItem (src/common/localStorage.ts) are isNative-gated no-ops. Desktop web is relay-fetch-only and in-memory; it cannot schedule a single reminder, by design, not by omission.

The permission prompt itself can only happen here, in the foreground JS layer (requestNotificationPermission, called from App.tsx once isNative && user && isInitialized) — none of the background workers on either platform are able to prompt for permission.

Recurrence engine — the real thing repeatingEventsHelper.ts

Unlike the two restricted native engines, the JS layer expands recurrence with the actual rrule npm package ("rrule": "^2.8.1") — full RFC 5545 grammar. getOccurrencesInRange() is what buildCandidates() in notifications.ts calls to compute reminder times, and the same module builds/parses the rule strings the event editor's recurrence UI produces.

The app just never generates anything outside FREQ/INTERVAL/BYDAY/COUNT/UNTIL — so the fuller grammar the library supports is never exercised by this app's own data, and the native engines' narrower subset never actually falls short of what a real event contains.

Android app.formstr.calendar

Twelve classes under android/app/src/main/java/app/formstr/calendar/: one activity, four Capacitor plugins, three WorkManager workers, one broadcast receiver, one app widget, and two utility classes.

MainActivity MainActivity.java · 257 lines

Extends BridgeActivity. Registers all four custom plugins in onCreate, before super.onCreate, then kicks off every background schedule in one place.

Boot sequence

Every launch: schedules the 6-hour NotificationWorker (kept if one already exists), fires one immediate one-time run of it, schedules the 15-minute InvitationWorker, schedules the 15-minute BookingWorker — the last two are cancelled and re-enqueued fresh on every launch rather than kept, so a relay-list or login change always takes effect immediately.

Three intent categories, one dispatch mechanism
  • HTTPS App Link — calendar.formstr.app/event/<naddr>, validated strictly (scheme, exact host, exactly two path segments, first segment literally event) and rebuilt into an internal /event/<naddr>?query route.
  • .ics file open — matched by text/calendar mime type or a content:///file:// URI ending in .ics; the file is read fully as text via the content resolver, escaped, and pushed in as raw content.
  • Internal openRoute extra — the string every notification and widget tap uses to jump to a specific screen (/bookings, /notifications, /notification-event/<id>).
The cold-start race

All three funnel into window.dispatchEvent(new CustomEvent(...)) calls injected via evaluateJavascript — but only once the JS layer has called the AppReady plugin's notifyReady(). Until then, routes and ICS content sit in pendingRoute/pendingIcsContent and flush the moment the app signals it's ready. The shared JS ICSListener passively listens for icsFileReceived on every platform; Android is currently the only native producer. This is the fix for a deep link firing before React has mounted its listeners.

NotificationWorker — the reconciliation engine NotificationWorker.java · 416 lines

The largest native class, and the only one with genuinely non-trivial logic. It "reconciles the complete desired calendar reminder set for a rolling 48-hour window" — the file's own description — rather than incrementally adding alarms.

Each run, for every cached event
  • Resolves notification preference: per-event override wins, else the owning calendar's preference, else enabled by default.
  • Resolves reminder offsets in minutes — configured per event, or the default [10, 0] (ten minutes before, and at start).
  • Expands recurrence for the window via RecurrenceUtils, extended past the 48h edge by whatever the largest configured offset is.
Diff, don't append

Builds a map of every alarm that should exist, keyed v2:<eventId>:<occurrenceStart>:m<offsetMinutes>, diffs it against the persisted registry (cal:scheduled-event-notifications-v2) of what's currently scheduled, cancels whatever's no longer desired, persists the new registry before scheduling a single alarm — so even an alarm due immediately can validate itself against a registry that already lists it — then calls AlarmManager for the rest.

Graceful degradation

Uses setExactAndAllowWhileIdle when exact-alarm scheduling is available, falls back to the inexact setAndAllowWhileIdle if the user revoked SCHEDULE_EXACT_ALARM (Android 12+). If POST_NOTIFICATIONS isn't granted at all, it doesn't retry or error — it clears every scheduled alarm and reports success.

Every run ends by calling CalendarWidget.refreshAll(), so the home-screen widget is never more than 6 hours stale even if the widget's own update tick hasn't fired.

NotificationReceiver — the fire step NotificationReceiver.java · 103 lines

The AlarmManager target. Before showing anything, it re-checks the notification key+id it fired with against the worker's live registry (isNotificationRegistered) and silently drops the broadcast if it's stale — the explicit guard against alarms left behind by an older app version or a reconciliation that ran a moment earlier.

InvitationWorker InvitationWorker.java · 318 lines Android only

Every 15 minutes, network-constrained. Polls up to 3 relays for gift-wrapped calendar invitations addressed to the logged-in pubkey.

Dual query, for migration compatibility

Two filters per relay: {kinds:[1059], #p:[you], #k:["1052"]} for current wraps, and {kinds:[1052], #p:[you]} for legacy pre-migration wraps that predate the #k classifier entirely. It also fetches legacy kind-84 tombstones the user authored on an old client, to keep old dismissals suppressed, and cross-checks the local cal:invitations cache so it never re-notifies about something a live session already surfaced. Wraps tagged ["booking","true"] are explicitly skipped — those belong to BookingWorker.

Fires one notification per run if anything new turns up ("You have 3 new invitations"), routing taps to /notifications. It never decrypts — the seal and rumor stay closed; only the outer wrap's public tags and event id are ever read.

BookingWorker BookingWorker.java · 315 lines Android only

Same 15-minute, network-constrained shape as InvitationWorker, same relay list, two separate concerns.

Requests vs. approvals

Booking requests — #k:"1057" plus legacy kind 1057 — always notify. Booking responses — #k:"1058" plus legacy kind 1058 — are fetched but filtered down to only those carrying ["status","approved"] before notifying; declines are silently dropped. Two distinct channels, "Booking Requests" and "Booking Acceptances", both routing taps to /bookings.

No tombstone query here

Unlike InvitationWorker, this worker never queries kind 84. The source comment is explicit: booking never had a pre-1059 kind-84 dismissal mechanism to stay backward compatible with, so there's nothing to read.

RecurrenceUtils RecurrenceUtils.java · 309 lines

A hand-written RRULE evaluator with no date library underneath it — plain java.util.Calendar arithmetic. Supports exactly what the app itself ever generates: FREQ ∈ {DAILY, WEEKLY, MONTHLY, YEARLY}, INTERVAL, BYDAY (meaningful only with WEEKLY), COUNT, and UNTIL in all three RRULE date shapes. No BYMONTHDAY, BYSETPOS, BYMONTH, BYWEEKNO, EXDATE, or RDATE — this is a deliberate subset, not a partial implementation of the full RFC.

Two entry points reused across three call sites: getNextOccurrenceInRange (the single soonest occurrence — used by CalendarWidget) and getOccurrencesInRange (every occurrence in a window — used by NotificationWorker), the latter built by repeatedly re-invoking the former and advancing a cursor, with a hard 10,000-iteration guard against a malformed rule that never advances.

RelayQueryUtils RelayQueryUtils.java · 113 lines

The entire Nostr client the background workers need — and nothing more. Raw OkHttp WebSockets, no signing, no relay pool, no reconnect/backoff. Rewrites wss:///ws:// to https:///http:// for OkHttp's request builder, sends one ["REQ", subId, filter], streams EVENT frames to a caller callback, sends CLOSE and disconnects the moment EOSE arrives — all bounded by a 15-second CountDownLatch timeout shared by both workers.

CalendarWidget CalendarWidget.java · 214 lines Android only

A home-screen AppWidgetProvider showing up to 3 upcoming events. Refreshed both by the OS's own APPWIDGET_UPDATE tick and explicitly at the end of every NotificationWorker run. Reads the same cal:events cache, independently re-deriving each recurring event's next occurrence — a third call site for RecurrenceUtils, alongside NotificationWorker and the JS calendar view itself — over a fixed 3-day lookahead. Row times render as a clock time (today), "Tomorrow", or a weekday abbreviation. Tapping anywhere launches MainActivity.

Permissions & manifest

Permissions declared

INTERNET, SCHEDULE_EXACT_ALARM, POST_NOTIFICATIONS, RECEIVE_BOOT_COMPLETED, READ_CALENDAR. No write-calendar permission — device calendar access is import-only, everywhere.

MainActivity intent filters

Launcher intent; an autoVerify HTTPS App Link for calendar.formstr.app/event/*; a text/calendar mime-type filter; and two more filters specifically for content:// and file:// URIs ending in .ics. Between them, the app registers as a full system "Open with" target for calendar files. Launch mode singleTask.

Receivers

NotificationReceiver is not exported — alarm-only, nothing external can trigger it. CalendarWidget's receiver is exported (required by the widget-host framework) and only responds to APPWIDGET_UPDATE.

iOS App

Two custom files exist under ios/App/App/, against Android's twelve. What's built mirrors Android closely; what's missing is most of it.

AppDelegate AppDelegate.swift · 52 lines

Standard Capacitor lifecycle scaffold. On launch it registers and schedules IOSNotificationScheduler's background-refresh task and runs an immediate reconciliation; entering background re-arms the refresh request; becoming active reconciles again.

URL and universal-link handling

Both application(_:open:options:) and application(_:continue:restorationHandler:) just forward straight into ApplicationDelegateProxy.shared — the stock @capacitor/app plugin's default JS-facing event. There is no Swift-side parsing of /event/<naddr> paths and no .ics file handling code anywhere in this file or the project.

App.entitlements does declare applinks:calendar.formstr.app, so the OS layer can intercept those links exactly like Android's autoVerify filter — but nothing native downstream translates the URL into an app route the way MainActivity does; that's left to the shared JS router.

IOSNotificationScheduler IOSNotificationScheduler.swift · 514 lines

A close Swift port of NotificationWorker's reconciliation algorithm — necessarily reimplemented rather than shared, since Java and Swift can't share a class. Same CapacitorStorage.cal:events / cal:calendar_lists / cal:notification-preferences keys (Capacitor's Preferences plugin prefixes iOS UserDefaults the same way), same 48-hour window, same [10, 0]-minute default offsets, same v2: key prefix and hash-to-int identifier scheme, and its own independent RRULE evaluator covering the identical subset — DAILY/WEEKLY/MONTHLY/YEARLY, INTERVAL, BYDAY, COUNT, UNTIL — as Android's RecurrenceUtils.

Where the platforms genuinely diverge

No AlarmManager equivalent exists on iOS, so scheduling uses UNCalendarNotificationTrigger fired by the system, and refresh runs opportunistically via BGAppRefreshTaskRequest rather than on a guaranteed cadence — iOS decides when it actually gets to run, not the app. The scheduler also caps itself at 64 pending notifications total and explicitly reserves headroom for any non-event notifications already pending — a real, system-enforced iOS ceiling Android's AlarmManager has no analog for.

What isn't there iOS gap

  • No InvitationWorker / BookingWorker equivalent — no relay polling at all when the app isn't foregrounded, so no background notifications for new invitations or bookings on iOS, ever.
  • No DeviceCalendarPlugin equivalent — no EventKit bridge exists in Swift, so the device-calendar-import feature (src/plugins/deviceCalendar.ts) has nothing to call into on iOS today.
  • No KeyBackupPlugin equivalent — the ncryptsec clipboard-copy / file-save flow has no native iOS implementation.
  • No CalendarWidget equivalent — no WidgetKit extension target exists in the Xcode project at all.
  • No .ics "Open with" registration — Info.plist declares no CFBundleDocumentTypes / UTExportedTypeDeclarations for .ics or text/calendar, so "Open in Calendar by Form*" for a calendar-file attachment isn't offered by iOS at all.

Create → deliver, step by step

One reminder, traced from the moment a user saves an event to the moment a notification appears — including what's different for a recurring event.

  1. Login populates the background feed

    onUserChange → syncUserNetworkState(pubkey) (src/stores/user.ts) fetches the user's own NIP-65 relay list, then writes bg:userPubkey, bg:relays, bg:lastLoginTime to Preferences. Without this write, Android's InvitationWorker/BookingWorker find no pubkey and no-op every run — though NotificationWorker doesn't need it; it only ever reads cal:events. App.tsx also calls requestNotificationPermission() here, the only place either OS's permission dialog can appear.

  2. User sets a reminder

    Opening the editor (EventEditor.tsx) seeds the offsets field from generalSettings.defaultReminderMinutes for a new event, or the event's own stored preference for an edit. NotificationPreferenceEditor edits a plain list of minutes-before values — there's no separate switch; an empty list is "no reminders."

  3. Recurrence is built in the same editor, if any

    frequencyToRRule/customRecurrence.ts constructs an RRULE string held as draftRecurrenceRule. The editor never produces anything outside FREQ/INTERVAL/BYDAY/COUNT/UNTIL — the same subset both native recurrence engines understand.

  4. Save runs a fixed sequence

    useEventSave.ts handleSave: publish the event → gift-wrap invites to new participants → add/move it into the calendar list → then, outside the relay-publish steps, write or clear the local offsets preference → cancel anything previously scheduled for this event → resolve the three preference levers → schedule fresh if the result is "enabled."

  5. Three levers, one resolver

    Per-event enable/disable (nostr tag, no UI sets it) beats per-calendar enable/disable (the calendar manage dialog, default enabled) beats the hard-coded default "enabled." See Preference levers & resolution for the full table.

  6. Every cache write triggers reconcile — redundantly, safely

    A single save fires reconcileNotificationSchedule() up to four times. Each is a no-op wrapper on Android that enqueues a unique one-time WorkManager job with REPLACE policy, so the four calls collapse into one real NotificationWorker.doWork() run — not four.

  7. The platforms fork completely

    • Android — JS computes a candidate list only for the UI preview; the real AlarmManager alarm comes from NotificationWorker.doWork() independently re-reading the cache and re-expanding recurrence with RecurrenceUtils.java.
    • iOS — JS calls LocalNotifications.schedule() directly, right here, and IOSNotificationScheduler.swift separately re-derives and re-schedules the same set on every launch/foreground/background/BGAppRefreshTask. Same deterministic keys, so both paths agree instead of colliding.
    • Web — none of this runs; nothing is even cached across a reload.

  8. Recurring events are never "scheduled once for the future"

    Both the JS candidate builder (NOTIFICATION_SCHEDULE_WINDOW_MS = 48h) and the native workers (SCHEDULE_WINDOW_MS, same 48h) only ever expand occurrences inside a rolling 48-hour lookahead. A monthly event's reminder six months out doesn't exist as a scheduled alarm today — it's created only once a periodic run (Android's 6-hour NotificationWorker, or iOS's next opportunistic BGAppRefreshTask) happens to land close enough for it to fall inside the window.

  9. Delivery

    Android — AlarmManager fires → NotificationReceiver re-validates the notification key against the live registry before showing anything, so a stale alarm from a cancelled/edited event silently drops → system notification → tap routes to /notification-event/<eventId>. iOS — the OS fires the UNCalendarNotificationTrigger directly with no app code running until tapped, at which point addNotificationClickListener reads notification.extra.eventId and navigates in-app.

  10. Cleanup

    Deleting an event cancels its notifications, clears the UI notification list, and deletes its offsets preference outright. Logging out cancels every pending notification, clears the native Android schedule, and wipes every bg:* key — after which InvitationWorker/BookingWorker have nothing left to poll with.

Wire-protocol tie-in

InvitationWorker and BookingWorker aren't a separate protocol — they're a cold-app backstop for flows the JS layer already handles live. See nostr-layer-reference.html for the full semantics; this is only what the native code specifically touches.

What the workers actually filter for
  • Invitations: {kinds:[1059], #p:[you], #k:["1052"]} — see Invitations (gift wrap).
  • Booking requests: {kinds:[1059], #p:[you], #k:["1057"]} — see Booking request.
  • Booking responses: {kinds:[1059], #p:[you], #k:["1058"]}, filtered client-side to status:"approved" — see Booking response.

All three share the literal outer kind 1059 and the same "one outer kind, three products" ambiguity documented in the protocol doc's gift-wrap notes — the native workers rely on exactly the same #k classifier tag the JS layer does to tell them apart, since decrypting to the rumor would tell them nothing (all three rumors share kind 14 now too). Every legacy dual-query the workers run (raw kind 1052/1057/1058 alongside the 1059+#k form) exists for the same reason the JS layer still reads it: pre-migration gift wraps predate the classifier tag and would otherwise silently stop surfacing.

Engineering notes

Registry-before-alarm, always

NotificationWorker persists its new scheduling registry before calling AlarmManager for a single alarm. Combined with NotificationReceiver's live registry check, this means a stale alarm from a cancelled reconciliation, an app downgrade, or a race between two runs simply no-ops on fire instead of showing a wrong or duplicate notification.

The recurrence engine exists three times, on purpose

NotificationWorker, CalendarWidget, and IOSNotificationScheduler each carry their own call into a RRULE evaluator (two independent Java/Swift implementations of the identical restricted grammar). None of them attempt the full RFC 5545 grammar — because the app itself never generates rules outside DAILY/WEEKLY/MONTHLY/YEARLY + INTERVAL/BYDAY/COUNT/UNTIL, implementing more would be dead code, not correctness.

Background workers never decrypt anything

InvitationWorker and BookingWorker's entire value is counting matching gift-wrap ids and firing a system notification — never touching the seal, the rumor, or the signer. That's what lets them run as plain WorkManager jobs with a bare OkHttp WebSocket, with no cryptographic dependency and no risk of leaking key material into a background process.

Android is the reference platform, not iOS

Every Android-only capability in the parity matrix above is a capability iOS simply doesn't have a native implementation for yet — not a deliberate platform-specific design choice documented anywhere in the source. The nostr-signer-capacitor-plugin being linked into the iOS build despite NIP-55 having no iOS ecosystem is the clearest sign of this: it's wired for platform symmetry at the JS/TS interface, not because it does anything on iOS.

A schema field with no writer dead path

The per-event notificationPreference tag is read on both the JS and native sides, and its "event overrides calendar" precedence is implemented identically in three languages (TypeScript, Java, Swift) — but no editor, dialog, or quick-edit view in src/ ever writes it. It's fully wired plumbing with nothing at the other end, the same shape as the already-documented dead anonymous booking mode in the protocol reference.

Multiple reconcile() calls per save is not a bug

A single event save can trigger reconcileNotificationSchedule() up to four times — once each from the event-cache write, the preference write, the cancel step, and the schedule step. This only stays cheap because Android's enqueueUniqueWork(..., REPLACE, ...) collapses any pending duplicate before it runs; the JS side never tries to be clever about de-duplicating the calls itself.
