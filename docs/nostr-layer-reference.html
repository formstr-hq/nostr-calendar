Calendar & events

Two parallel universes exist side by side: a custom encrypted kind (32678) for private events, and a simplified take on NIP-52 (31923) for public ones. They share no fields at the protocol level.

Private event — create kind 32678

Triggered by: saving a new event in the editor with the private toggle on.

Identity

Parameterized-replaceable. d = random/derived hash. Coordinate = 32678:<author>:<d>.

Outer tags (public)

Only ["d", dTag] — everything else lives inside encrypted content.

Content (NIP-44 self-encrypted, per-event view key)
tagmeaning
title, descriptionplain stringsrequired
start, endunix secondsrequired
imagestring, "" if noneoptional
L / l"rrule" label / rrule string, if recurringoptional
notificationreminder preferenceoptional
formnaddr, plus form's read-only view key (never the edit key) — one per attached formoptional, repeats
locationfree text, repeatsoptional
pcreator first, then one per invited participantrequired
Encryption

selfEncrypt: NIP-44 to a freshly generated per-event view keypair (encrypt-to-self with a throwaway key, not the user's real identity). Only holders of the nsec-encoded view key can read the event.

Participants

Each participant (creator included) gets a NIP-59 gift wrap invitation — see Invitations.

Relays

publishSignedEvent → worker routing (user relays ∪ author outbox ∪ recipient inbox). NIP-65 lists for invited pubkeys are fetched first to warm outbox routing before the gift wraps go out.

Public event — create kind 31923

Triggered by: saving a new event with the private toggle off.

Identity

d = persisted id or a fresh UUID. All-day and timed events both use 31923 — the NIP-52 date-only kind (31922) is never used.

tagmeaning
title, d—required
start, endunix seconds, as stringsrequired
image—optional
locationrepeatsoptional
pparticipant, no role/relation qualifier, repeatsoptional
Content

Plaintext description string (not JSON). No encryption.

Participants

Listed only as public p tags — no gift-wrap invitation is sent for public events; that mechanism is private-event-only.

Private event — edit

Triggered by: author edits an existing private event.

Re-runs the create builder with the same d tag and the same view key, republishing 32678 as a replacement. created_at is forced strictly greater than the prior version to beat NIP-01's same-second tie-break.

Only participants not in the previous participant list get a new invitation. Removed participants receive no revocation — the app has no un-invite mechanism (kind 84 exists only for reading legacy tombstones).

Host-applying a participant's suggested new time (from an RSVP) is just this flow with start/end overwritten — private events only.

Public event — edit

Same publish function as creation, replacing on the same d tag with a newer created_at. No participant-notification step exists for public events, same as on create.

Event duplication

UI convenience only — pre-fills the editor with the source event's data but no d/id, so saving runs through ordinary create (32678 or 31923). No distinct wire behavior.

Event deletion / removal kind 5

Triggered by: the delete dialog, three mutually exclusive options.

Delete for everyone (author only)

NIP-09 kind 5 with ["e", eventId], ["a", "<kind>:<author>:<d>"], and ["k", kind] per targeted kind. content is an optional free-text reason. Also removed from the owning calendar list and its busy-list range retracted.

Remove from calendar (non-author, or author opting out)

Only drops the event's a-tag reference from the calendar list (32123) and clears the busy range. No deletion event, other copies untouched.

Ignore (invitation not yet accepted)

Deletes the invitation gift wrap itself — see Invitations → Dismiss.

Client-side enforcement layer

Local-relay only natively enforces NIP-09 by e tag. This app layers its own client-side tombstone tracking (localStorage, per-account) for a-tag deletions of addressable events and legacy kind-84 removals.

Identity

Invitations — discover, accept, dismiss, report kind 1059 legacy 1052

Discovery

Two parallel subscriptions — {kinds:[1059], #p:[you], #k:["1052"]} and {kinds:[1052], #p:[you]} for legacy wraps (which lack a k classifier, so can't be merged into one filter).

Unwrap (NIP-59)

Outer wrap decrypted with your signer → seal → rumor. Rumor is kind 14 (NIP-17's chat-message kind, reused so generic NIP-17 clients render it as a DM), tags: a (event coordinate), viewKey, optional signing_nsec; content is a human-readable invite line, e.g. "X has invited you to Y on Z".

signing_nsec — the self-deletion trick

The wrap's own one-time signing key is embedded, encrypted, inside the rumor. Relays require a deletion to be signed by the target event's own pubkey — since the wrap is signed by a random ephemeral key the recipient doesn't hold, the app hands them that key after decryption so they can self-sign a NIP-09 deletion of the wrap later.

Accept

Adds an a-tag ref to the chosen calendar list (32123). Nothing is published back to the sender — acceptance is local only.

Dismiss

New-style invites: self-signed kind-5 deletion under the embedded ephemeral key. Legacy invites (no signing_nsec): the user's own signer publishes a kind-5 tagging k:1059/1052 — this can't actually delete someone else's signed event, so it only suppresses it client-side.

Report

Runs Reporting against the resolved event coordinate, then dismisses the same way.

Reporting / flagging kind 1984 · NIP-56

Triggered by: "Report" on a pending invitation (no report entry point once an event is already in a calendar).

tagmeaning
p[authorPubkey, reportType]
a[coordinate, relayHint?, reportType]

reportType ∈ nudity, malware, profanity, illegal, spam, impersonation, other. content is optional free text. Fully public, unencrypted. Own past reports are fetched back to filter out already-reported items.

Private calendar lists kind 32123

Identity

One per calendar a user creates. d = random hash. Outer tags: ["d", id] only.

Content — different encryption idiom from events/RSVPs

NIP-44, but encrypted via the live signer to the user's own real pubkey (signerEncrypt) rather than a raw held key — works through NIP-07/bunker round trips too. JSON tag array: title, content (description), color, optional notifications:"disabled", and one ["a", coordinate, relayUrl, viewKey] per member event.

Mutations

Add/remove/move-between-lists all read-modify-republish the whole list event — no partial updates.

Deletion

NIP-09 kind 5 with a (list coordinate) and e (last known id).

No public/followable calendars

There is no NIP-51-style public list, and no mechanism to subscribe to someone else's calendar — 32123 lists are private and single-owner only.

Forms attached to an event kind 30168 / 1069

Not authored by this app's nostr layer — read-only integration with Formstr. Attachment is a ["form", naddr, viewKey?] tag inside the encrypted content of a private event, so attachment itself is invisible to non-participants. Only the form's read-only key is stored, never the admin/response key. Submission (kind 1069 signing) happens inside @formstr/sdk, outside this repo's direct control.

Identity & sessions

Pure key-management — no calendar events published here. Every other flow signs through whatever SignerManager.getSigner() returns.

Login methods

Browser extension (NIP-07)

Waits up to 2s for window.nostr, then all signing routes through it directly. No event published by login itself.

Remote signer (NIP-46 bunker / NostrConnect QR)

Uses a dedicated relay pool, separate from the app's local-relay worker — "the signer's RPC channel is not app data." Requested perms: sign_event, nip44_encrypt, nip44_decrypt, get_public_key. Bunker's own relay list is later fed into gossip routing as discovery hints, never as a publish target.

Native nsec (mobile only)

Decodes the nsec, wraps it in an in-process signer, persists to native secure storage. Blocked entirely on web.

ncryptsec (NIP-49)

Paste or upload a .txt file plus a passphrase; decryption of the NIP-49 payload happens inside @formstr/signer, not this repo.

Android native signer (NIP-55)

Discovered via a Capacitor bridge, native-only — deliberately never initialized on web.

Create account

Key generation, NIP-49 encryption, and any kind-0 profile publish for name/picture/about all happen inside @formstr/signer — not traceable in this repo. The app only receives the resulting ncryptsec string and forces the user to copy or download it before continuing.

Session restore

Branches per stored method: extension re-injects, Android reconstructs from stored pubkey/npub without reopening the signer app, NIP-46 reuses a stored client secret so the bunker doesn't re-prompt, ncryptsec can't auto-unlock (needs the passphrase, always falls through to the login modal).

A legacy-migration path reads pre-@formstr/signer localStorage keys and native-stored nsecs, migrates them into the new signer, then deletes the old keys — except guest raw-keypair sessions, kept alive deliberately.

Logout

Clears the active signer/local key and cached user data. No Nostr event published. A separate caller-triggered step tears down the relay worker and wipes its IndexedDB cache — a data-layer action, not a protocol one.

Scheduling & booking

A Calendly-style layer bolted onto the calendar. Reuses the calendar's gift-wrap machinery (same outer kind 1059) but with entirely custom rumor kinds and its own two-tier key hierarchy.

Scheduling page — create / update / delete kind 31927 kind 32680

Identity

Parameterized-replaceable per (pubkey, d). Outer tags: ["d", id] only. created_at forced strictly increasing on every edit.

Content — fully encrypted, own view keypair

A fresh secp256k1 keypair is minted at creation and reused on every edit — "a page's view key is its share-link capability." Every field is NIP-44 self-encrypted (inline, hand-rolled — not via the shared selfEncrypt helper) as a tag array:

tagmeaning
title, timezone, duration_mode—
min_noticehard-coded "0" — field is disabled in the UI
max_advance, buffer, expiryexpiry 0 = never
slot_durationrepeats, one per configured duration
avail["avail","recurring",day,start,end] or ["avail","date",dateStr,start,end], repeats
blockeddate string, repeats
location, image, event_title, descriptionoptional
form[naddr, viewKey?], repeats
relayone per currently configured relay — app-specific hint, not NIP-65
Key recovery sidecar — kind 32680

Every publish also republishes a 32680 record, d = the page's own d, content = {v, viewKey, dTag, createdAt} — this time self-encrypted with the real identity key via the signer, not the page's own view key. Its only job is letting the owner recover the view key on a new device. Deletion sets content:"" as a tombstone.

Sharing

/schedule/<naddr>?viewKey=<nsec-encoded> — the view key travels in the URL query string, nsec-encoded as a convenient bech32 container (not a real identity key). Public/browsable pages are explicitly unsupported — a page without a viewKey query param hard-fails to load.

Deletion

NIP-09 on the page event, followed by a best-effort tombstone of the 32680 key record.

Booking request — guest → host kind 1059 · k=1057

Triggered by: a visitor on a scheduling-page link picks a slot and submits (login required).

Pre-generated future event identity

Before the host ever approves, the booker mints the d tag and view key for what will become the eventual private calendar event (32678) — so booker and host land on the exact same event identity once approved. The booker adds this ref to their own calendar immediately, as a forward-looking placeholder.

Rumor kind 14 deprecated 57
tagmeaning
ascheduling page coordinate 31927:host:pageD
start, endunix seconds
title, notemay be empty
dpre-generated future-event id
viewKeypre-generated future-event NIP-44 key
signing_nsecephemeral wrap key, for host-side self-deletion later

Rumor content is empty — everything lives in tags. Recipient is the host's real pubkey, on the outer wrap's p tag. The dedicated BookingRequestRumor kind (57) is now deprecated in favor of the same shared Rumor kind (14) calendar invitations use — request vs. response vs. invite is told apart entirely by the outer wrap's k tag, not by rumor kind.

Booker identity — two modes, one unwired

self (default): sealed with the booker's real signer, so the rumor is technically linkable to their real pubkey. anonymous: seals with a freshly generated one-time keypair for true unlinkability — fully implemented at the protocol layer, but no UI path ever passes this mode, and the matching key-save function is never called anywhere. Dead code today.

Booking response — host → guest kind 1059 · k=1058

Approve — a composite, multi-event publish
  • Publishes the private calendar event (32678), reusing the booker's pre-generated d/view key so both sides share identical event identity.
  • Adds it to the host's own calendar list (32123).
  • Publishes a busy-list entry for the slot, best-effort (see Free/busy).
  • Publishes the response gift wrap — rumor kind 14 deprecated 58, status:"approved", plus event_ref (the new event's coordinate) and viewKey (same key as the event, so the booker can decrypt it) and signing_nsec.
Decline

Same wrap shape, status:"declined", optional reason tag, no event_ref/viewKey.

Booker-side matching

Incoming responses are matched to a locally-tracked outgoing booking by content — page ref + start + end + pending status — there's no protocol-level thread/reply id linking request to response.

Free/busy publishing kind 31926

One event per user per calendar month, d = "YYYY-MM". Tags: ["d","YYYY-MM"], ["t","YYYY-MM"], ["t","busy"] (NIP-12 discovery hashtags), and one ["block", startUnix, endUnix] per busy range. content is always empty — "no titles/descriptions leaked," by design. The one booking-adjacent event that's fully public and unencrypted, so even anonymous visitors on a booking page can compute availability with no key. Fired automatically on booking approval, and optionally when creating/editing/RSVPing to a calendar event via an opt-in checkbox — meaning a private (32678) event's time range can leak publicly through this side channel if the user opts in.

Infra & account data

General settings sync kind 30078 · NIP-78

Identity

d = "calendar/general_settings", one event total per user (not per device).

Content

{weekStart, timeFormat, defaultCalendarId, defaultDuration, defaultReminderMinutes, workingHours}, NIP-44 self-encrypted via the live signer to the user's own pubkey.

Sync semantics

Last-write-wins via strictly-increasing created_at. A local-edit-during-fetch race guard means any local change made while a remote fetch is in flight always wins over the value that fetch returns. Publishes are serialized through a queue so concurrent edits don't race each other.

Not everything syncs

Theme mode, accent color, layout, and filters live only in localStorage — only the nested "general" settings object round-trips through Nostr. Theme/accent/layout do not follow the user across devices.

Relay list management kind 10002 · NIP-65

One ["r", url] tag per relay, empty content. No read/write markers are ever written — every tag is bare, so the app doesn't distinguish read relays from write relays; it treats the list as one undifferentiated set.

The user's own list and the app's connection policy are the same list

On login, syncUserNetworkState(pubkey) fetches the logged-in user's own kind-10002 event via fetchRelayList and writes it straight into useRelayStore (falling back to the seven hard-coded defaults if the user has no NIP-65 event yet) — and getRelays(), what actually gets fed to the local-relay worker as its connection set, reads from that same store. Saving on the Relay Settings page runs the sync in reverse: it writes the edited list to useRelayStore and publishes it as a fresh kind-10002 event in the same action. So this is one bidirectionally-synced list, not two separate mechanisms.

Other users' NIP-65 lists — routing hints only

Fetching other pubkeys' kind-10002 lists (fetchRelayList/fetchRelayLists for gift-wrap recipients, naddr relay-hint resolution) is purely a gossip/outbox-routing input — those never get written into useRelayStore or folded into the app's own connection set. Only the logged-in user's own list round-trips into local config.

Per-event publish fan-out (inside the worker, outside this repo): user relays ∪ author's own outbox ∪ each p-tagged recipient's inbox. Delivery is durable — "zero acceptance means queued for retry, not failed."

Profile fetch & NIP-05 verification

Profile: plain kind-0 read, content parsed ad hoc as JSON. No profile-publish path exists anywhere in src/nostr/ — the only kind-0 write is buried inside @formstr/signer's account creation; there's no visible "edit profile" flow.

NIP-05: fetches /.well-known/nostr.json with redirect:"error" — explicitly refuses to follow redirects as anti-spoofing hardening beyond the bare spec. A profile's self-reported nip05 field is never trusted at face value; this resolver is the only trusted verification path, used to show a verified badge on booking requesters.

Cross-cutting design notes

Three encryption idioms, used inconsistently

  • Raw self-encrypt — caller holds a bare secret key (a view key), NIP-44 to itself. Used for private events, private RSVPs, scheduling pages (though scheduling pages hand-roll this rather than calling the shared helper).
  • Signer self-encrypt — NIP-44 via the live signer to the user's own real pubkey. Used for calendar lists, general settings, and the scheduling-page key-recovery sidecar. Works with NIP-07/bunker, has a concurrency gate to avoid firing multiple simultaneous signer permission popups.
  • NIP-59 gift wrap (rumor → seal → wrap) — used for calendar invitations and both booking request/response directions.

One outer kind, three products, one deletion trick

All three gift-wrap products — calendar invites, booking requests, booking responses — now share the literal outer kind 1059 and the literal rumor kind 14. The dedicated rumor kinds each product used to have (57 for requests, 58 for responses) are now deprecated in favor of that one shared kind 14 — the same move already made for calendar invites. That leaves the wrap's own k tag (1052 / 1057 / 1058) as the only signal that tells the three apart; decrypting all the way down to the rumor no longer helps, since it's the same kind in every case. A generic NIP-17 client subscribed to kind 1059 would receive all three intermixed with no standard way to distinguish them at all. Legacy dedicated outer wrap kinds are still read for back-compat but never written.

Every wrap type leaks its own one-time signing key (signing_nsec) to the recipient, post-decryption only, purely so the recipient can self-sign a NIP-09 deletion later — otherwise gift wraps are effectively undeletable by anyone but the sender, since relays require same-pubkey-as-target on deletions.

Where this diverges from NIP-52

  • No date-only calendar kind (31922) — every public event is 31923, timed or not.
  • No standard calendar-container kind (31924) — the "calendar" concept here (32123) is private, self-encrypted, and unrelated to NIP-52's public grouping model.
  • No t/hashtag reference tags anywhere on events, private or public.
  • Public RSVPs drop NIP-52's optional label/freebusy tags down to a, status, start, end, d.
  • No comments/notes protocol object (e.g. NIP-22) — the "notes" UI is just the event's own description field.

Known gaps & dead code

  • No participant revocation — removing someone from a private event's participant list on edit sends no notification; kind 84 is read-only-legacy, never published fresh.
  • Anonymous booking is unreachable — fully built at the protocol layer, but no UI path ever selects it and its key-save function is never called.
  • No profile-publish or edit-profile flow is visible anywhere in this repo's own source.
  • Theme/accent/layout settings don't sync across devices — only the "general" settings sub-object does.
  • Legacy NIP-09 fallback deletions are best-effort no-ops — a signer-authored deletion of someone else's gift wrap is architecturally expected to be rejected by conformant relays; it only suppresses the item client-side.
